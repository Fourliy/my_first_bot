# Техническое видение

Документ — отправная точка для разработки Telegram LLM-ассистента из `docs/idea.md`. Цель: максимально простое решение для проверки идеи.

## Технологии

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| Зависимости | uv (`pyproject.toml` + lock-файл) |
| Telegram | aiogram 3, long polling |
| LLM | пакет openai, API OpenRouter |
| Конфиг | переменные окружения |
| Логи | стандартный модуль `logging` |
| Запуск | Make (локально и через Docker) |
| Контейнер | Docker и docker-compose только для локального запуска |

Других библиотек нет: ни БД, ни Redis, ни веб-фреймворка, ни webhook.

Стек выбран так, чтобы бот можно было запустить у себя на компьютере, без публичного сервера и без лишних сервисов.

## Сборка и деплой

Цель: обеспечить простой локальный цикл разработки и возможность проверять приложение в изолированном контейнере локально; деплой на удалённый сервер не нужен для MVP.

Подходы:

- Локально: работать в виртуальном окружении (`venv`) и управлять зависимостями через `uv`; для удобства использовать `make`‑цели для создания окружения, установки зависимостей и запуска приложения.
- Контейнерно (локально): собирать Docker‑образ с Python 3.12 и зависимостями для prod‑like тестирования локально; запускать контейнер с прокидыванием переменных окружения из файла `.env` (никаких секретов в образе). Docker — только для локального запуска/тестирования.
- Гибрид: разрабатывать в venv, периодически проверять образ в Docker перед релизом.

Рекомендации:

- Хранить в репозитории файл `.env.example` с перечислением переменных; реальные секреты — только в локальном `.env`, не коммитить.
- `Make` использовать как единый интерфейс для запуска в venv и для сборки/запуска в Docker (`venv`, `install`, `run`, `docker-build`, `docker-run`, `clean`).
- В `Dockerfile` не хардкодить секреты; прокидывать их через `--env`/`--env-file`.
- Опционально добавить CI, который выполняет `uv install`, запускает тесты и собирает Docker‑образ; в CI не хранить production-секреты.

Конец раздела "Сборка и деплой".

## Принцип разработки

- Цель: минимальное рабочее решение для проверки идеи — запуск локально, без лишних сервисов.
- KISS: избегаем лишних слоёв и абстракций; добавляем только то, что напрямую нужен для MVP.
- OOP, один класс — один файл: `Config`, `LLMClient`, `TelegramBot`, `Runner`, `models`.
- Ясные границы ответственности:
	- `Config` — чтение и валидация окружения;
	- `LLMClient` — вызовы `openai`/OpenRouter, таймауты, обработка ошибок;
	- `TelegramBot` — обработка сообщений через `aiogram` (polling) и перевод в/из внутреннего формата;
	- `Runner` — сборка компонентов и запуск long-polling.
- Конфиг и секреты — только через переменные окружения; `.env` возможен для локальной разработки (не коммитить реальные секреты).
- Нет персистентности в MVP: диалоги хранятся в памяти; добавление БД — отдельный ADR при необходимости.
- Обработка ошибок: таймауты и понятные ответы пользователю при ошибках LLM; логирование исключений для отладки.
- Тестируемость: отделяем I/O от логики, `LLMClient` и Telegram-интеграции должны легко мокироваться.
- Минимум зависимостей: только `aiogram`, `openai`, `uv` (и `python-dotenv` — по согласованию).


## Структура проекта

Минимальная, KISS-ориентированная структура проекта, соответствующая `docs/vision.md` и `conventions`:

```
pyproject.toml
.env.example
Makefile
Dockerfile
docs/vision.md
src/my_first_bot/
		__init__.py
		config.py        # Config: класс чтения переменных окружения
		logger.py        # Настройка logging
		llm_client.py    # LLMClient: обёртка openai / OpenRouter
		telegram_bot.py  # TelegramBot: aiogram handlers (polling)
		runner.py        # Runner: собирает компоненты и запускает polling
		models.py        # Датаклассы: DialogMessage, Dialog (in-memory)
		utils.py         # Вспомогательные функции (по необходимости)
tests/
```

Компоненты и взаимодействие (упрощённая схема):

```
User
	|
	v
Telegram (Bot API)
	|
	v
[aiogram Dispatcher]
	|
	v
TelegramBot handlers
	|
	+--> Config (env: TELEGRAM_TOKEN, OPENROUTER_API_KEY, MODEL_NAME, LOG_LEVEL)
	|
	+--> logger (инициализация через logger.py)
	|
	v
LLMClient (llm_client.py)  -- запросы через openai к OpenRouter
	|
	v
OpenRouter / LLM provider
	|
	v
Ответ -> LLMClient -> TelegramBot -> User
```

Ключевые принципы:
- OOP: один класс — один файл (`Config`, `LLMClient`, `TelegramBot`, `Runner`).
- Без персистентности: диалоги — в памяти (ADR/vision подразумевают отсутствие БД в MVP).
- Конфиг через переменные окружения; `.env` — опционально для локальной разработки.
- Минимум зависимостей: `aiogram`, `openai`, `uv`.
- Запуск: `make` (venv) или Docker для локального запуска.

## Архитектура

Краткая сводка. Приложение — однопроцессный асинхронный сервис (asyncio), использующий long-polling `aiogram` для приёма сообщений. Архитектура минимальна и модульна: каждый модуль выполняет одну роль и легко тестируется.

Основные компоненты:
- `Config` — чтение и валидация окружения (токены, модель, лог-уровень).
- `logger` — централизованная настройка логирования.
- `LLMClient` — обёртка над `openai` для работы через OpenRouter: сбор `messages`, запросы, таймауты, ретраи, обработка ошибок.
- `TelegramBot` — регистрация хэндлеров, преобразование Telegram-сообщений в внутренние объекты и отправка ответов.
- `Runner` — инициализация компонентов и запуск polling.

Поток обработки запроса:
1. Сообщение от пользователя приходит в Telegram Bot API.
2. `aiogram Dispatcher` вызывает хэндлер в `TelegramBot`.
3. `TelegramBot` преобразует вход в `DialogMessage` и обновляет in-memory `Dialog` (chat_id -> история).
4. `TelegramBot` вызывает `LLMClient.chat(messages)` с подготовленным списком сообщений (system + history + user).
5. `LLMClient` делает HTTP-вызов через `openai` к OpenRouter, ждёт ответ с таймаутом и возвращает текст.
6. `TelegramBot` отправляет ответ обратно пользователю и обновляет историю.

Надёжность и ограничения (KISS-подход):
- Таймауты для LLM-запросов (например 20–30s) и вежливое сообщение пользователю при ошибке.
- Ограничение истории по количеству сообщений или приблизительному числу токенов; при превышении удаляем старые сообщения (FIFO).
- Ретраи для transient-ошибок с ограничением числа попыток и экспоненциальной задержкой.
- Логирование — без секретов; логируются события запроса/ответа (summary), ошибки и latency.

Конкурентность и масштабирование:
- В MVP один процесс/контейнер; aiogram обеспечивает асинхронную обработку нескольких чатов.
- Для горизонтального масштабирования потребуется вынести состояние диалога в внешнее хранилище и перейти на webhook/балансировщик — отдельный ADR.

Тестируемость:
- Бизнес-логика отделена от сетевого I/O; `LLMClient` и `TelegramBot` легко мокируются в тестах.

Формат сообщений к LLM:
- Используем OpenAI Chat формат: список {"role": "system|user|assistant", "content": "..."}.
- `SYSTEM_PROMPT` задаётся в `Config` или в коде и добавляется к началу последовательности сообщений.

Безопасность:
- Секреты только в окружении; не логировать ключи и полные пользовательские сообщения с чувствительным содержимым.

Дальше заполняем остальные разделы: модель данных, работа с LLM, сценарии, конфигурация, логирование, сборка и деплой.

## Модель данных

- Подход: в MVP состояние хранится в памяти; используем простые датаклассы для описания сообщений и диалогов. Персистентность добавляется только по отдельному ADR.
- `DialogMessage` (датакласс):
	- `message_id: int` — ID сообщения в Telegram (если доступен)
	- `chat_id: int` — идентификатор чата
	- `role: Literal['system','user','assistant']` — роль автора
	- `content: str` — текст сообщения
	- `timestamp: datetime` — время получения/отправки

Стек выбран так, чтобы бот можно было запустить у себя на компьютере, без публичного сервера и без лишних сервисов.
- Модуль: один файл `logger.py`, который настраивает корневой логгер `my_first_bot` и предоставляет фабрику/конфигуратор для модулей.
- Уровень и формат:
	- Уровень управляется через `Config.LOG_LEVEL` (по умолчанию `INFO`).
	- Формат по умолчанию — человекочитаемый текст; опционально через `LOG_FORMAT=json` можно включить JSON-подобный формат (без сторонних зависимостей).
- Хэндлеры:
	- `StreamHandler` (stdout) — обязательный.
	- Опционально `RotatingFileHandler` для локальной отладки (ограничение размера и числа файлов).
- Политика логирования:
	- `INFO`: старты/остановки, события приёма/отправки (summary: `chat_id`, `message_len`, `truncated`).
	- `DEBUG`: подробности для разработки (латентность, исходные метаданные), но по умолчанию не логировать полный текст сообщений.
	- `ERROR`: исключения с `exc_info=True`; хранить stacktrace, не записывать секреты.
- Маскирование секретов: встроить `Filter`, который маскирует/удаляет чувствительные поля в сообщениях перед выводом (ключи, токены, полные тексты с PII).
- Структурированные поля: при возможности логировать `event`, `chat_id`, `message_len`, `truncated`, `model`, `latency_ms`, `status` — это упростит последующую агрегацию.
- Метрики: логировать success/failure и latency для вызовов LLM.
- Тестируемость: `logger.py` легко мокируется; логика маскировки покрывается unit-тестами.
- Эволюция: при необходимости можно добавить интеграцию с внешними системами (Sentry, ELK), но в MVP не подключаем.

## Сборка и деплой

Цель: простой локальный цикл разработки и возможность запускать приложение в изолированном контейнере локально. Деплой на удалённые серверы не требуется для MVP.

Подходы (KISS):

- Локальный (рекомендуется для разработки): `venv` + `uv` + `make`.
	- Пример действий (PowerShell):
		```powershell
		python -m venv .venv
		.\.venv\Scripts\Activate.ps1
		uv install
		make run
		```
	- `make run` предполагает запуск `python -m my_first_bot.runner` в активированном виртуальном окружении.

- Контейнерный (локально, prod‑like тест): Docker image с Python 3.12.
	- Сборка и запуск (bash / PowerShell аналогичны):
		```bash
		docker build -t my_first_bot:local .
		docker run --rm --env-file .env --env TELEGRAM_TOKEN --env OPENROUTER_API_KEY my_first_bot:local
		```
	- В контейнере переменные окружения прокидываются через `--env-file` или `--env` — никаких секретов в image.

- Гибрид: разработка в venv, периодическая проверка образа через Docker.

Make targets (минимально рекомендуемые):
- `venv` — создать виртуальное окружение.
- `install` — установить зависимости через `uv` в активном venv.
- `run` — запустить `runner` в venv.
- `docker-build` — собрать локальный образ.
- `docker-run` — запустить контейнер с `--env-file .env`.

Рекомендации:
- В репозитории хранить `.env.example` с перечнем переменных; реальные секреты — только в `.env` локально и не коммитить.
- В `Dockerfile` не добавлять секреты; использовать `--env-file` или CI/CD секреты при необходимости публикации образа.
- `Makefile` должен поддерживать запуск как с Docker, так и без (см. цели выше).
- Для CI (опционально) запускать `uv install`, `pytest` и `docker build` в отдельной задаче.
