
# ADR 0001. Стек MVP для Telegram LLM-ассистента

- Статус: принято
- Дата: 2026-09-17
- Авторы: TBD
- Связано: `docs/idea.md`, `docs/vision.md`

## Контекст

Нужно проверить идею из `docs/idea.md`: интерактивный диалог в Telegram, где ответы генерирует LLM с поведением, заданным системным промптом. Приоритет — как можно быстрее получить работоспособный прототип локально, с минимальным количеством внешних сервисов и зависимостей.

Требования к MVP:
- Быстро запустить на локальной машине разработчика.
- Минимум инфраструктуры (без базы, без постоянного хостинга).
- Простота замены LLM-моделей через единый интерфейс.

## Решение

Выбрана простая, прагматичная связка технологий (см. `docs/vision.md`). Решение фиксирует стек и рабочие допущения до проверки идеи:

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| Зависимости / менеджмент | минимальный менеджер среды и `pyproject.toml` + lock-файл |
| Telegram | aiogram 3, long polling |
| LLM | официальный пакет `openai` и прокси OpenRouter (единный интерфейс к разным моделям) |
| Конфиг | переменные окружения (токены, ключи) |
| Логи | стандартный `logging` |
| Запуск | Make (локально) и опционально Docker для локального окружения |
| Контейнеры | Docker & docker-compose только для локальной разработки |

В MVP не включают базу данных, Redis, веб-фреймворк и webhook; история диалогов между перезапусками не сохраняется.

OpenRouter используется как прокси для разных провайдеров: это упрощает смену модели (меняется только конфигурация), сам OpenRouter не генерирует текст.

## Rationale (обоснование)

- Python — короткая разработка, богатая экосистема библиотек для Telegram и LLM.
- `aiogram 3` — современный, асинхронный и лёгкий фреймворк для Bot API; long polling быстрее запускать локально.
- Использование OpenRouter даёт гибкость смены моделей без рефакторинга кода.
- Отсутствие DB/Redis упрощает старт и ускоряет валидацию идеи; при положительном результате можно отдельно принять решение о хранении истории.

## Alternatives considered

- `python-telegram-bot` — поддерживаемая альтернатива, но стиль API не даёт существенного преимущества для прототипа.
- Node.js/TypeScript (grammY, Telegraf) либо Go — имеют смысл при существующем стековом опыте команды.
- Webhook + хостинг — избран, когда нужен 24/7 доступ; для проверки идеи избыточно.
- Прямое использование OpenAI/Anthropic/Gemini — можно перейти позже, OpenRouter упрощает смену.

## Implementation notes

- Конфигурация хранится в `.env`/переменных окружения: `TELEGRAM_TOKEN`, `OPENROUTER_KEY`.
- Запуск локально: `make run` / `python -m my_bot` (описать в README при реализации).
- Тесты: покрыть основные сценарии обработки сообщений и интеграционные тесты с mocked LLM.

## Consequences

- Положительные:
	- Быстрый запуск прототипа локально, низкий порог входа для разработчика.
	- Гибкость в смене LLM-провайдера через OpenRouter.
	- Меньше инфраструктурных затрат на этапе валидации.

- Отрицательные / риски:
	- Отсутствие хранения истории ограничит сценарии, требующие контекста между перезапусками.
	- Long polling при локальном запуске не годится для production с высокой нагрузкой.
	- Зависимость от OpenRouter и счёт за модели — затратный фактор в длительной эксплуатации.
